thigns I want. think of these as my ideal way of writing this software. we can talk abut them. 

- I want a very easy and self maintained build system using cmake and ninja and then higher commands using make. for example `make initialize` for setting up the repo, bulding the libs, building the dev tools (for example bulding the tracy profiler server and desktop gui). if cmake can do this job easily with good deverloper expereince then we can replace it. note that these commands should be platform aware. if some commands does not support windows for example. another thing is that I don't want to use git submodules anymore! I want to downlaod the source code through the build system initialize command. I still want to look at one file and see all the dependencies, name, version, source link, branch (if they are from a spcific branch).

- I want a full debug, performance profile, release mode builds for every platform integrated with vs code. I am using tracy as my main profiler. switching between them should be easy (possibly one command on terminal or vs code ) which takes care of providing that setup (even if it requires rebuild). One thing that I really want (haven't been able to implement) is to stub/mock or hook into any memory allocation function like malloc and inject a TRACY_ALLOC macro. reason for this is to provide a instrumentation for capturing 3rd party/libs memory alocation thorught out the runtime. this is only needed during performance profile build mode! my atempt of doing this caused a lot of trouble (infinit recusrive malloc for example :)

- I want a full in-app memory stat and observation. menaing that when the app request for memory, it should do it through one system that manages and tracks that memory this is a very low level design! meaning the I as a developer won't be dealing with this in day-today. internal libs will use this memory system to allocate memory. reason being is that I might be using differnt memory allocators or patterns or do arena based allocation (or other strategy), but the memory layer should provide that facility which internal libs can use and benefit from. meanwhile memory system can track these allocation, tag them based on what kind of memory it is, life time between allocation and deallocation. it needs to be very lightweight, but very robust and well thought API design that can last and adapt with new requirement. another reason is that with memory system, we want to abstract away as much as we can from the platform. if onr platform gives us advantages, then we should be able to use that advantage. API should be able allow for improvement in performance ifa platform allows for it and if not, fallback to default or lower mode if platform does not support certain memory operation or allocation scheme. 

- any use of C++ std lib should be justified! most important factor is memory usage! on the fly in the hotpath allocation using smart pointers are strictly forbidden. we need a strong stance and framework on where and how and for what reason heap allocation can happen! App performance is the highest importance. so we don't just want use c++ features ( I mean anything C++ offers) willy nilly. every paradigm and std lib and programming pattern from C++ must go through scrutiny. I will give you one example to just understand what I mean: use of virtual functions in rendering loop is forbidden unless it is very unlikely to happen (user opening a menu item from context menu which happens rarely, but using virtual function which compiler cannot see and optimize and incure a runtime cost, should be avoided unless we have a good reason to use it). Note my tone here, nothing is stricly forbidden here, anything within reason can be utilized to achive our goal. 

- windowing system and Ui must support native windowing features of the platform. app should be able to manage multiple windows (I know imgui has viewports but that should be used when we need anything that does not need a native window). App should support multiple screens and must have DPI support, App should support themes and we only support various dark themes. themes should have a file (single file) that can be loaded at runtime to alter the theme and UI shapes (as much as dear imgui allows it). lights themes are left for community to make. 


- threading and asyncio, and intrinsis. I want to use threading and cpu intrinsics (e.g. avx instructions) for places that can benfit the most. we can decide where threading can be useful and how. expsially wheter we need to separate the ui thread and work thread or keep it like a traditional game engine loop where UI and logic are one thread but aything IO or compute heavy goes to worker threads. for expanded widebit instruction set, one thing is very very important and that is it should be used a performance boost and for any process or path that uses intrinsics, there should be a defaul non-intrin path for it. we can decide and talk about whether a runtime check or compile time assinment is a good option for various scenarios. for async io, that is a fancy feature that we can develop or add a external lib for it. that is mostly for ease of use for networking.

- plugin system. I want this software to be fully expandable and modifiable using plugins! plugis can be in various forms and touch various systems! for the first versions, plugins can be run for adding UI features, new pages, new functionality, adding complete set of components and logic and even networking. there are hooks and places where these plugins can fit into. one important thing which I have not decided and don't have enough experise on is the architecutre of the software when plugins are introuced. things like managing the context and scope of application state by plugins, file and user platform access, mode of activation/deactivation. basically, how do we develop a well architected plugin sdk so community can actually use it and extend the functionality of the program. another thing about the plugin system is that we can allow non-permissive plugins to run. default application source code is MIT. but to enable propritaty tech, a plugin system is the best options. 

- logging and error report and crash logs. we need to be able capture logs and write it into a file on a roation basis to a file (e.g. max 10 miB and can be configured by the user as well) and only dring low intensity work (we will define later what counts as low intensity work, but one example is when user is in edit mode and is desining stuff, not running the stage and performing). crashlogs and reporting should be very detailed and informative.

- hardware interface (usb, wifi, etc). we need full support for the laptop/computer comm hardware. these will be used to send/recieve data through usb and wifi and bluetooth. definitly we can bring in external libs but we should measure the tradefoffs on usability, performance, and feature set. since the app is running on regular pc, most comms are happening through widely accepted media and transport hardware. all other porotocols will be supported through software or extension of the application (e.g. MIDI is a software protocl built and abstracted on usb, wifi, and blutooth).

- testing the app | headless mode. a robust testing framework that test the logic of the app. UI testing happens manually. but unit, integration. e2e, simulations (senario), smoke testing, needs to happen before every merge to main. we will talk about what is the best opion and frameworks for testing the app. 

- networking. well this is not much of a suprise, we need networking facilities to send and receive data from local/web network! it needs to be extremely fast and good support for all kinds of protocls. very nice api and absolutly non-blocking. 

- filesystem and temp files, vaults. platform filesytem must be abstracted and all file paths and trivial locations (home, temp, system, configs, etc, ) should be normalized in the app in unix format (even windows paths must be convered and handled like linux.) so a trnslation layer must sit for all platforms. 

- graphics backend: right now we are using opengl for all of graphics and ui (dear imgui). but this should be a swappable backend where the entire application can switch from let's say opengl to directx or vulcan. for the first version, we don't need to think about it too much. but have that in the background for later versions and if we see performance is dropping only becuase of the graphics API! 

- architecutre for this application is generally like a game engine. we have a game loop aware of previous computation time for the last frame and it will register inputs and then computes the logic and then renders. I want the systems to have clear boundaries and responsibilites. API surface is well thought and has always room for expansion and when required (not for all systems), they allow for plugins to interface with them!
